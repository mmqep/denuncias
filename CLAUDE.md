# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Server-rendered **Flask on Turso / libSQL** (embedded replica) app for citizen
complaint/grievance ("quejas y denuncias") intake and internal institutional case
management for MMQEP. Jinja2 templates with static HTML/CSS/JS — no SPA, no JS
framework, no build step. Targets **Python 3.11+**. Local use only. UI text and
domain vocabulary are in Spanish.

## Commands

```powershell
# venv (Windows)
py -3.11 -m venv venv; venv\Scripts\activate
pip install -r requirements.txt

# One-time: load schema + seeds into the cloud Turso DB
turso db shell <db-name> < schema.sql

# Run dev server -> http://127.0.0.1:5000/denuncias/
# (creates/syncs the local embedded replica on first start)
python app.py
```

There is **no test suite and no linter**. Configuration lives in `.env` (copy
`.env.example`, not versioned); `config.py` only loads it via `python-dotenv` and
re-exports the same symbols the app expects. There is **no migration framework**
and `schema.sql` is SQLite/libSQL DDL — it is the single source of truth for the
schema; schema changes are applied by editing `schema.sql` and re-running it
against Turso (`turso db shell`).

## Architecture

The entire application lives in **`app.py`** (~2500 lines). Understand its layout
before editing:

- **`create_app()`** — app factory. Creates two `Blueprint`s, both URL-prefixed
  under `/denuncias`: `public_denuncias` (`/denuncias`) and `admin_denuncias`
  (`/denuncias/admin`). A module-level `app = create_app()` is what
  `python app.py` runs.
- **`register_public_routes(bp)` / `register_admin_routes(bp)`** — all routes are
  defined as nested functions inside these two registrars, not at module top
  level. To add/find an endpoint, edit inside the relevant registrar. Route
  endpoint names are referenced as `public_denuncias.<fn>` / `admin_denuncias.<fn>`
  in `url_for`.
- Top of file: shared helpers (catalog building, area/responsible resolution,
  reassignment-on-deactivation, follow-up logging) used by the route registrars.

**DB access pattern** (`db.py`): one libSQL embedded-replica connection per
request stored on Flask `g`, opened lazily via `get_db()`, closed in a
`teardown_appcontext`. `db.py` is a **compatibility shim** that keeps the old
PyMySQL-style API so `app.py` is essentially untouched: `CursorWrapper` is a
context manager, translates `%s` → `?`, returns rows as real `dict`s (so both
`row["col"]` and `row.get()` work), adapts `datetime/date/time` params to ISO
text on write and reconstructs them by column name on read (`fecha_*`,
`hora_hecho`), and re-raises constraint violations as `db.IntegrityError`.
`ConnWrapper.commit()` calls `conn.sync()` to push to Turso; `connect_db()`
syncs on open and sets `PRAGMA foreign_keys=ON` per connection (required for the
`ON DELETE SET NULL`/`CASCADE` behavior the app depends on). Raw parameterized
SQL throughout, no ORM. When editing `app.py` SQL, keep `%s` placeholders (the
shim translates them) and avoid MySQL-only syntax (e.g. `IF()` — use
`CASE WHEN`).

**Auth & authorization** are session-based, not Flask-Login:
- `session['uid']`, `session['rol']`, `session['area_id']` are set at login.
- Decorators `@login_required` and `@roles_required(*roles)` gate admin routes.
- Three roles: **Administrador** (full inbox/assignment/users/states),
  **Responsable** (only cases for their `area_id` or assigned to them),
  **Consulta** (read-only). Visibility is enforced in two places that must stay
  consistent: `usuario_puede_ver_denuncia()` (single record) and
  `listar_where_base()` / `sql_y_args_bandeja_denuncias()` (list + Excel report
  filters). Changing role scoping means updating both.

**Domain model** (`schema.sql`): `areas`, `categorias` → `subcategorias`,
`usuarios`, `denuncias`, `seguimientos`, `archivos_adjuntos`. Key invariants:
- ENUM columns are modeled as `TEXT` + `CHECK (... IN (...))`; the allowed value
  lists must stay in sync with `ESTADOS_PERMITIDOS`/`PRIORIDADES` in `app.py`.
- A `denuncia` stores `categoria`/`subcategoria` as **text snapshots** copied at
  registration time (plus nullable FK ids) so historical records survive catalog
  edits/deletes (FKs are `ON DELETE SET NULL`).
- Each `denuncia` has a unique public `codigo` like `MMQ-XXXXXXXX` generated by
  `codigo_denuncia_unico()`; citizens use it to query status.
- **`seguimientos`** is the append-only audit trail. Any state change,
  assignment, reassignment, or internal note must call `registrar_seguimiento()`.
  Public intake is logged with `usuario_id` NULL.
- Deactivating a `usuario` triggers `reasignar_denuncias_abiertas_por_desactivacion()`
  — open cases are moved to a valid candidate; don't bypass this when touching
  user activation logic.

**File uploads**: saved under `static/uploads/` (must be writable). Allowed
extensions and per-file size cap come from `.env` via `config.py`;
`MAX_CONTENT_LENGTH` is set to 5× the per-file cap in `create_app()`.

**PDF / Excel generation**: `pdf_comprobante.py` (citizen receipt),
`pdf_reporte_bandeja.py` (internal/external case reports) via ReportLab; Excel
inbox export via openpyxl inside the admin reports route. Excel exports apply the
same role visibility filters as the inbox.

The app lives under the `/denuncias` path prefix (both blueprints), not the
domain root — `/` redirects to the public portal. Local use only; there are no
deployment artifacts.

## Conventions

- Source comments, flash messages, commit-relevant strings, and templates are in
  **Spanish**; match that when editing user-facing text.
- Keep raw SQL parameterized with `%s` placeholders (the `db.py` shim translates
  them to `?`) — no string interpolation of user input into queries.
- Concentrate any DB-dialect concerns in the `db.py` shim, not in `app.py`.
- Schema changes: edit `schema.sql` (libSQL/SQLite DDL) and re-apply it to Turso;
  there is no migration system.
